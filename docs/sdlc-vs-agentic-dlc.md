# Классический SDLC, agentic DLC и STC — поэтапное сравнение

Исследование, 2026-09-28. Цель: разложить по этапам, что в STC соответствует
классическому SDLC и «агентному» циклу разработки, что у STC своё и чего в STC
нет.

Источники по STC — файлы этого репозитория (ссылки в тексте). Внешние
источники — в конце документа.

---

## 1. Сначала о терминах: как это правильно называть

Под «agentic DLC» в индустрии понимают **две разные вещи**, и их легко спутать.

| Термин | Что значит | Кто продвигает | Про что |
|---|---|---|---|
| **SDLC** | Software Development Life Cycle | классика (ISO/IEC/IEEE 12207, waterfall, V-model, Agile, DevOps) | как люди делают ПО |
| **AI-DLC** | *AI-Driven Development Life Cycle* | AWS (методология + открытые правила `awslabs/aidlc-workflows`) | как делать ПО, когда основную работу выполняют агенты, а люди утверждают |
| **Agentic SDLC** | общее название того же сдвига | Microsoft/GitHub («agentic DevOps»), консалтинг | то же, что AI-DLC, без привязки к вендору |
| **SDD** (spec-driven development) | спецификация — главный артефакт, код выводится из неё | GitHub Spec Kit, Kiro | часть agentic SDLC: этапы до кода |
| **ADLC** ① | *Agentic* Development Lifecycle | OX Security, Cycode | agentic SDLC с упором на безопасность и управление |
| **ADLC** ② | *Agent* Development Lifecycle | IBM, Salesforce Agentforce, Arthur, Atlan | жизненный цикл **самого агента**: промпты, контекст, оценки (evals), мониторинг вероятностного поведения |

**Вывод по терминам.** Для «как мы разрабатываем ПО с агентами» правильнее
всего говорить **AI-DLC** (если имеется в виду методология AWS) или **agentic
SDLC** (в общем смысле). Сокращение «ADLC» лучше не использовать без
расшифровки: половина источников под ним понимает цикл разработки самих
агентов.

🎯 **STC интересен тем, что живёт в обоих смыслах сразу:**

- для **проектов** пользователя STC — это agentic SDLC (PEV, спецификации,
  TDD, ревью, деплой);
- для **самого себя** (харнесса) STC ведёт ADLC во втором смысле: живые
  канарейки, замеры поведения агента по транскриптам, мутационная проверка
  правил, еженедельные аудиты. То, что другие называют «evals и мониторинг
  агента», в STC уже есть — просто направлено на собственную конфигурацию.

## 2. Три подхода коротко

### 2.1 Классический SDLC

Фазы (в типовой редакции): **планирование и ТЭО → требования → проектирование
(HLD/LLD) → реализация → тестирование → развёртывание → сопровождение**.
Исполнители — люди по ролям (PM, аналитик, архитектор, разработчик, QA,
DevOps). Ритм — фазы (waterfall) или спринты по 1–4 недели (Agile). Контроль —
ревью документов, код-ревью, CI, CAB. Главный ресурс — человеко-часы.
V-модель связывает каждый уровень проектирования со своим уровнем тестирования.

### 2.2 AI-DLC (AWS) и близкие SDD-фреймворки

- **Три фазы:** *Inception* (что и зачем строим), *Construction* (как строим),
  *Operations* (развёртывание и мониторинг). Во второй редакции правил
  (`aidlc-workflows` 2.0) добавлены Initialization и Ideation — всего 5 фаз.
- **Ритуалы:** *Mob Elaboration* — ИИ из намерения (intent) предлагает
  пользовательские истории и разбиение на единицы работы, задаёт уточняющие
  вопросы, команда валидирует; *Mob Construction* — ИИ предлагает доменную
  модель, дизайн, код и тесты по каждой единице, команда принимает решения.
- **Словарь:** спринт → **bolt** (часы–дни), эпик → **unit of work**.
- **Принцип:** «ИИ предлагает и спрашивает — человек решает». После каждой
  стадии — явное одобрение.
- **Адаптивность:** агент сам выбирает, какие стадии нужны под сложность
  запроса. В редакции v1 стадии Inception: Workspace Detection, Reverse
  Engineering (для существующего кода), Requirements Analysis, User Stories,
  Workflow Planning, Application Design, Units Generation; Construction — по
  каждой единице: Functional Design, NFR Requirements, NFR Design,
  Infrastructure Design, Code Generation, затем Build and Test. Operations в
  v1 — заготовка на будущее.
- **Состояние и след:** все артефакты в `aidlc-docs/`, плюс файл состояния
  процесса и журнал аудита. Расширения по желанию: security baseline,
  property-based testing, resiliency baseline.
- **Spec Kit / Kiro** покрывают ту же зону до кода: `constitution` (незыблемые
  принципы) → `specify` (что и зачем) → `plan` (технический план) → `tasks`
  (упорядоченные задачи с зависимостями) → `implement`. У Kiro:
  `requirements.md` (EARS) → `design.md` → `tasks.md`.

### 2.3 STC

STC — не методология на бумаге, а **конфигурация агента, которая
разворачивается в харнесс** (Claude Code, Codex) и навязывает цикл через
правила, команды, субагентов и хуки. Ядро цикла:

- **PEV: Plan → Execute → Verify** (`core/rules/pev.md`) с масштабом задачи
  **S/M/L** и правилами повышения до L;
- **SDD → TDD:** `/to-spec` → `/to-tasks` → навык `tdd`
  (README § «SDLC via SDD → TDD»);
- **режим оркестратора** (FR-28): дорогая модель планирует, `builder`
  исполняет по одному блоку с протоколом DECIDED/FORK;
- **независимая проверка:** ревью ×3 (`code-reviewer` + `security-arch` +
  `qa`) без контекста, `security-deps` перед деплоем, `e2e`;
- **Roundtable** — согласование идеи и плана критиками от разных вендоров
  (в разработке, `docs/roundtable.md`);
- **петля знаний:** транскрипты → офлайн-ингест → ежемесячный ревью в
  Obsidian; реестр дефектов с эскалацией «правило → хук».

## 3. Поэтапное сопоставление

Обозначения в колонке «Как соотносится»:
🟰 — прямое соответствие · 🔄 — есть, но переосмыслено · ⭐ — своё у STC ·
🕳️ — в STC слабо или нет.

### Этап 0. Постоянные правила проекта («конституция»)

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| стандарты кодирования, Definition of Done, архитектурные принципы | `constitution.md` (Spec Kit), steering-правила (AI-DLC, Kiro) | always-context: `behavior.md`, `pev.md`, `session.md` + профиль пользователя; `code_standard.md` с профилем проекта (S0/S1/S2 + флаги 💰👤📤🔐🌐📝📈); инструкция проекта; `DESIGN.md` |

**Как соотносится: 🔄 + ⭐.** Идея та же, что у constitution. Отличия STC:

- правила **исполняются хуками**, а не только читаются моделью. ADR-001:
  «правило в тексте рецидивирует, правило в хуке — нет». 22 хука
  (`core/hooks/`), из них guard-хуки жёстко блокируют действие;
- правила **разделены по стоимости контекста**: три файла грузятся всегда,
  остальное (playbook, стандарт кода, каталоги) — по ссылке по требованию.
  Ни в SDLC, ни в AI-DLC токены не являются ограничением проекта;
- профиль проекта сам выбирает, какие блоки стандарта применяются в ревью.

### Этап 1. Инициация и понимание контекста

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| бизнес-кейс, ТЭО, границы проекта | Intent; Workspace Detection; Reverse Engineering для существующего кода | `core/templates/new-project.md` (Фаза 0 — kickoff); `SNAPSHOT.md` проекта; граф кода graphify + хук H18; команда `/zoom-out`; H19 plan-recall (что уже решали по теме); H22 prompt-lens (размытые формулировки в запросе) |

**Как соотносится: 🟰 + 🔄.** Инициация нового проекта в STC близка к
классике (стек, деплой, блок-план, критерии готовности каждого блока).

Для существующего кода у AI-DLC есть **отдельная стадия с артефактом**
(Reverse Engineering), а у STC — **инструменты без обязательного артефакта**:
граф кода, снимок, zoom-out. Знание о кодовой базе в STC строится по
требованию и не фиксируется как документ этапа. ⭐ У STC зато есть то, чего
нет у других: перед постановкой задачи агент **ищет прошлые решения** по теме
(H19), а запрос пользователя проверяется детерминированно, без модели (H22).

### Этап 2. Выбор масштаба процесса

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| выбор модели процесса на весь проект (waterfall / agile); tailoring процесса | адаптивная глубина: агент сам решает, какие стадии выполнять; Workflow Planning | таблица **S/M/L** в `pev.md` + правила повышения до L (архитектура, API, схема данных, граница безопасности, необратимость, ≥2 исполнителя, открытая развилка); ≥3 развилок → grill-me / Council |

**Как соотносится: 🟰 с AI-DLC, 🔄 к классике.** Обе агентные модели решают
масштаб процесса **на каждую задачу**, а не на проект. Разница: в AI-DLC
глубину выбирает модель по своему суждению, в STC — по **явной таблице с
критериями**, а для Roundtable масштаб указывает автор в манифесте, и при
неясности по умолчанию выбирается **более дорогая проверка**
(`docs/roundtable.md` §15).

### Этап 3. Требования

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| SRS, use cases, НФТ, матрица трассировки; интервью аналитика со стейкхолдерами | Requirements Analysis, User Stories (Mob Elaboration); вопросы — в файле, ответы — туда же; EARS у Kiro | `/grill-me` (вопросы по одному, к каждому — рекомендуемый ответ; на что можно ответить кодом — агент смотрит в код); `/to-spec`: use cases + AC; **abuse cases → негативные AC**; **failure modes** по каждому use case; **security baseline-5 как AC**; FR-30 — эхо-переформулировка перед дорогой работой |

**Как соотносится: 🟰 по форме, ⭐ по содержанию.** Use cases + AC — это
классика. Своё у STC:

- **два рефлекса на каждый use case** (`code_standard.md` §9): «как это
  сломать?» (каталог злоупотреблений → негативные AC и НФТ) и «где это
  застрянет?» (каталог типовых сбоев). В SDLC это делают отдельные threat
  modeling и FMEA, если вообще делают; в AI-DLC безопасность — опциональное
  расширение;
- **безопасность вшита в AC при передаче**, а не проверяется только в конце:
  «правила есть в каталоге, но молча выпадают, если не зафиксированы как AC»;
- **исследование документации — на этапе требований**, и это не пожелание:
  хук H16 не даст править код интеграции без сохранённого исследования.

🕳️ Нет формальной матрицы трассировки «требование → тест»: AC — это чеклист
с тегом `#ac`, связь с конкретными тестами не отслеживается.

### Этап 4. Оценка решения (до проектирования)

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| анализ альтернатив архитектором, иногда ATAM; make-or-buy | Application Design, где ИИ предлагает, а команда выбирает | **buy-vs-build** обязателен (H14, пункт спеки DEP-4); **Council** — пять ролей критиков + вывод председателя; `/prototype` (LOGIC / UI); агент `research`; **Roundtable, стадия «идея»** со «слепым вопросом» |

**Как соотносится: ⭐ — самый своеобразный этап STC.**

- **Слепой вопрос Roundtable** (`core/scripts/roundtable/tables/stages.yaml`):
  критику сначала показывают задачу, ограничения и критерий успеха, но **не
  показывают решение автора**, и просят предложить своё. Только потом —
  сравнить. Обоснование из самого проекта: десять кругов ревью искали дыры в
  решении, которое не стоило выбирать, потому что критики, увидев готовое
  решение, начинали его улучшать («привязка»).
- **Сигнал нежизнеспособности:** если оба критика независимо назвали другой
  подход — сразу к пользователю, до подсчёта блокеров.
- **Бюджет перевёрнут:** экономят на плане и ревью, а не на идее — отказ от
  решения на этом шаге стоит ноль выброшенной работы.
- **Council** — дивергентное мышление без пользователя; **grill-me** —
  конвергентное, с пользователем. Порядок явно задан: grill-me → Council →
  план.

Ни классический SDLC, ни AI-DLC не содержат механизма против привязки к
первому решению; в AI-DLC ИИ как раз предлагает решение первым.

### Этап 5. Проектирование

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| HLD/LLD, модель данных, ADR, дизайн интерфейсов, НФТ-дизайн, инфраструктура | Application Design → Units Generation → по каждой единице Functional Design, NFR Requirements/Design, Infrastructure Design; `design.md`/`plan.md` в SDD | ADR (`project_docs.md`: Решение → Почему → Что отвергли, `ADR-NNN`); ERD через mermaid.ink с `layout: elk`; `DESIGN.md` для UI; `/improve-codebase-architecture` (глубокие модули по Оустерхауту, язык глоссария); профиль стандарта кода |

**Как соотносится: 🟰 по ADR и модели данных, 🕳️ по НФТ и инфраструктуре.**

- ADR у STC — классический формат с жёстким триггером: «понадобится ли новой
  сессии понять, ПОЧЕМУ так?». Плюс журнал решений (H23): при ответе на
  развилку записываются и выбранный, и **отвергнутые** варианты с причиной,
  чтобы их не предложили снова через месяц.
- 🕳️ **Нет отдельного этапа НФТ-проектирования и инфраструктурного
  проектирования.** Частично это закрывают флаги профиля (📈 LOAD, 🌐 API) и
  блок OBS в стандарте кода, но артефакта «NFR design» нет — у AI-DLC это две
  отдельные стадии на каждую единицу.
- ⭐ Архитектурный ревью по кодовой базе целиком — периодический (примерно
  раз в три крупные задачи), а не только в начале проекта.

### Этап 6. Декомпозиция и план работ

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| WBS, оценка трудоёмкости, планирование спринта, бэклог | Workflow Planning; units of work; bolts; `tasks.md` с зависимостями | блоки `A/B/C` и подблоки `B0 → B1 → B2` (`project_docs.md`); `/to-tasks` → строки задач с полями `block`, `exec`, `priority`; FR-27 — **кто и на какой модели исполняет каждый блок**; хук H21 не выпускает из режима плана без AC/DoD, разбиения «блок → исполнитель» и строки «развилки закрыты» |

**Как соотносится: 🟰 по разбиению, ⭐ по назначению исполнителя.**

- Разбиение с зависимостями — как в `tasks.md` Spec Kit и units of work
  AI-DLC.
- ⭐ **План — это документ для передачи дешёвому исполнителю.** Поэтому в нём
  обязательны исполнитель и модель для каждого блока, а H21 проверяет, что
  план исполним без дорогой модели. В SDLC аналог — назначение задачи
  конкретному разработчику, но выбор «уровня квалификации» исполнителя под
  каждую задачу там не формализован.
- 🔄 Вместо оценки в часах — **бюджет вызовов/токенов**: Roundtable считает
  6–14 вызовов на задачу с жёстким потолком 30 (`docs/roundtable.md` §15).
- 🔄 Ритм: «одна сессия — один блок» (`new-project.md`) ≈ bolt в AI-DLC.

### Этап 7. Согласование плана

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| design review, sign-off стейкхолдеров, CAB для рискованных изменений | явное одобрение человеком после **каждой** стадии | развилки решает пользователь (карточка развилки 🗳️, журнал решений H23); для M/L — выход из плана через H21; **Roundtable, стадия «план»**: критики Claude и Codex, побитово одинаковый пакет с хешем, вердикт **вычисляет программа** по таблице, молчание или сбой ≠ согласие |

**Как соотносится: 🔄 + ⭐.**

- AI-DLC ставит ворота **на каждую стадию**; STC — на **выход из плана и на
  развилки**. Внутри исполнения блоки идут без одобрения, если не возник FORK.
  Это осознанный компромисс: меньше остановок, но и меньше контрольных точек.
- Техническая мелочь фиксируется как `DECIDED`, архитектурное отклонение
  возвращается как `FORK`, а деньги, персональные данные, юридические и
  видимые пользователю вопросы — всегда к человеку (`pev.md` § Plan).
- ⭐ Roundtable — то, чего нет нигде: **независимость критиков доказана
  измерением** (шип изоляции Ш1: у критика нет инструментов, нет доступа к
  репозиторию и к ответу второго критика), а правила процесса лежат в
  YAML-таблицах, покрытие которых тестами измеряется мутациями (100 %).
  Самоотчёту модели о своих инструментах не верят — проверено, что он врёт.

### Этап 8. Реализация

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| разработчики пишут код, pair programming, feature branches | Code Generation (Mob Construction): ИИ пишет, команда решает | **режим оркестратора**: main планирует и интегрирует, `builder` исполняет **один блок** в своей области записи; `cleanup` — механические правки; параллельные исполнители — в отдельных worktree с непересекающимися областями; **TDD** («нет продакшн-кода без падающего теста», вертикальные срезы); переиспользование прежде изобретения (H04, H10); документация прежде кода интеграции (H16); H07 — грязное дерево; H14 — main не правит код проекта сам после плана |

**Как соотносится: 🔄 по роли человека, ⭐ по дисциплине исполнителя.**

- В AI-DLC ИИ генерирует, а человек принимает решения в «мобе». В STC
  **иерархия агентов**: главный агент — оркестратор, субагенты — исполнители.
  Человек вмешивается только на FORK.
- ⭐ **Протокол DECIDED/FORK** — исполнитель не угадывает архитектуру, а
  останавливается и возвращает развилку; обнаруженное ограничение, ломающее
  план, → перепланирование затронутых блоков, независимые продолжают идти.
- ⭐ **Экономика контекста на уровне инструментов:** H11–H15 блокируют сырой
  вывод в контекст, повторные чтения, веб-запросы из main, дорогие скрипты в
  main. Классика про это не знает, AI-DLC — тоже.
- TDD есть и в классике (XP), и опционально в AI-DLC; у STC он жёсткий и с
  запретом горизонтальных срезов («сначала все тесты, потом весь код»).

### Этап 9. Тестирование и проверка

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| unit → integration → system → UAT; V-модель; QA-команда; код-ревью | Build and Test; опционально property-based testing | **Verify обязателен даже для S**: static / eyes / dynamic / independent; L — минимум два вида, включая независимый; **ревью ×3** свежими субагентами **без контекста**; `e2e` через Playwright (три канала: CLI, реальный браузер, субагент); `/code-review`; после трёх неудачных починок — эскалация, а не четвёртая попытка; навык `diagnose` («нет починки без корня») |

**Как соотносится: 🟰 по видам проверок, ⭐ по независимости.**

- Виды проверок почти совпадают с классическими уровнями; e2e ≈ системное
  тестирование.
- ⭐ **Ревьюеры намеренно без контекста** проекта, чтобы не было привязки;
  стандарт кода для них — рубрика, а не контекст. В классике ревьюер обычно
  погружён в код; в AI-DLC отдельного независимого ревью нет (во v2 есть два
  агента-ревьюера).
- ⭐ Разделение «машина / ревьюер» (`code_standard.md` §1): всё, что ловит
  линтер, не тратит время ревью.
- 🕳️ **Нет приёмочного тестирования с пользователем (UAT)** как этапа:
  приёмку делает main по AC. Сценарии e2e по проекту — в приватном
  `user/projects/<name>.md`.
- 🕳️ Мультивендорное ревью **реализации** (Roundtable, стадия «ревью», блок
  Б14) — вне MVP. Сейчас разные вендоры проверяют идею и план, но не код.

### Этап 10. Релиз и развёртывание

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| release management, CI/CD, CAB, окно релиза, откат | Operations: автоматизация развёртывания | **push в main = релиз** — только по явному слову пользователя, хук H01 с одноразовым подтверждением; `security-deps` — жёсткие ворота перед деплоем; деплой **только через версионированный скрипт с откатом** (сломан скрипт → чиним скрипт, а не правим прод руками); e2e перед деплоем; обычный деплой с доказанным откатом не требует эскалации модели |

**Как соотносится: 🟰.** Это самая «классическая» часть STC: release gate,
runbook, откат, проверка зависимостей. Для собственного деплоя STC всё это
реализовано особенно тщательно (`deploy/deploy.py`: dry-run по умолчанию,
резервная копия до записи, отказ при конфликтах, `restore`, идемпотентность).

### Этап 11. Эксплуатация и сопровождение

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| мониторинг, инциденты, SLA, патчи, сопровождение | Operations: мониторинг, наблюдаемость, готовность к продакшну (в v1 — заготовка) | **для продукта:** блок OBS в стандарте кода, навык `diagnose`, `security-deps` после массового обновления зависимостей. **Для самого агента:** еженедельный аудит, AgentShield, живые канарейки Claude и Codex, `hook_health`, `answer_health`, `decision_health`, ежемесячный `infra-audit`, фоновое обновление графа кода и снимков |

**Как соотносится: 🕳️ для продукта, ⭐ для агента.**

- 🕳️ **Эксплуатация продукта в STC почти не описана**: нет шаблона
  мониторинга, реакции на инциденты, пост-мортема продукта. Это самый
  заметный пробел против обоих подходов.
- ⭐ Зато **эксплуатация агента** — развитый ADLC во втором смысле: STC
  измеряет, действительно ли его правила работают. Принцип из README: «мера,
  которую ни разу не видели падающей, считается недоказанной».

### Этап 12. Обратная связь и накопление знаний

| Классический SDLC | AI-DLC / SDD | STC |
|---|---|---|
| ретроспективы, post-mortem, lessons learned, база знаний | артефакты `aidlc-docs/` как постоянный контекст; журнал аудита; «выученные правила» в v2 | **реестр дефектов** (`reference_defect_ledger.md`): симптом → **класс** причины → самый дешёвый слой защиты (🤖 машина > 👁 чеклист > 📝 текст) → при повторе эскалация влево вплоть до «правило → хук»; транскрипты → офлайн-ингест → **ежемесячный ревью человеком** (модель не пишет каноническую память сама); ADR и журнал решений; `📌 MEMORY` |

**Как соотносится: 🔄 к ретроспективе, ⭐ по механике.**

- Ретроспектива в классике — ритуал команды; в STC — **протокол на каждый
  пойманный дефект**, с явной лестницей эскалации. Это ближе к
  shift-left/poka-yoke, чем к ретро.
- Знание переживает не только сессию, но и **смену вендора модели**: оси
  «харнесс × провайдер» разделены, одни и те же правила разворачиваются и под
  Claude, и под Codex.

## 4. Сквозные измерения

| Измерение | Классический SDLC | AI-DLC | STC |
|---|---|---|---|
| **Кто делает работу** | люди по ролям | агенты, люди валидируют «мобом» | главный агент-оркестратор + типизированные субагенты; один человек решает развилки |
| **Роли** | PM, BA, архитектор, dev, QA, sec, ops | 11 агентов-экспертов, 2 ревьюера (v2) | реестр агентов (`core/agents/registry.yaml`): builder ≈ dev, qa ≈ QA, security-arch/deps ≈ AppSec, e2e ≈ системный тестировщик, research ≈ аналитик, cleanup ≈ младший dev; Council — «виртуальные стейкхолдеры»; Roundtable — внешние рецензенты |
| **Ритм** | фазы или спринты 1–4 недели | bolts: часы–дни | задача S/M/L; «одна сессия — один блок» |
| **Глубина процесса** | на проект | на запрос, решает модель | на задачу, по явной таблице + правила повышения |
| **Как навязывается процесс** | регламент, CI, ревью | правила-тексты, которые читает агент + одобрения | хуки (блок / подсказка / пропуск) + тексты; эффективность хуков измеряется |
| **Где правда о работе** | Jira/Confluence, документы | `aidlc-docs/`, файл состояния, журнал аудита | markdown в хранилище (`specs/`, `tasks/`), документы репозитория, память проекта (STATE / OPEN / CHANGELOG), транскрипты |
| **Главный дефицитный ресурс** | человеко-часы | внимание человека на одобрениях | **токены и контекст**, затем внимание пользователя |
| **Контроль качества ревью** | опыт ревьюеров | ревью-агенты | ревьюеры без контекста; мультивендорные критики с доказанной изоляцией; вердикт вычисляется программой |
| **Переносимость** | — | один набор правил на несколько IDE/агентов | «харнесс × провайдер»: форма и модель разделены; деградация формы без потери возможности |

## 5. Итог: общее, уникальное, пробелы

### 5.1 Что общее у всех трёх

1. **Требования до кода.** Везде есть этап «что и зачем», и результат
   фиксируется артефактом (SRS / `spec.md` / спека из `/to-spec`).
2. **Декомпозиция с зависимостями** (WBS / units of work / блоки A0–B2).
3. **Проверка перед выпуском** и ворота на релиз.
4. **Человек принимает ключевые решения**: в классике он же и исполняет, в
   AI-DLC и STC — утверждает.
5. **Запись решений** (ADR в классике и STC, `aidlc-docs` в AI-DLC).

### 5.2 Что STC разделяет с AI-DLC, но не с классикой

- масштаб процесса выбирается **на задачу**, а не на проект;
- исполнитель — агент, человек утверждает;
- короткий цикл (bolt ≈ сессия-блок);
- артефакты процесса — это **контекст для следующего агента**, а не
  отчётность;
- защита от потери контекста между сессиями.

### 5.3 Что есть только у STC

1. **Правила исполняются хуками**, и правило, которое рецидивирует,
   переводится в хук (ADR-001, `reference_retired_codes.md`).
2. **Против привязки к решению:** слепой вопрос критикам, ревьюеры без
   контекста, «сигнал нежизнеспособности».
3. **Мультивендорное согласование с доказанной изоляцией** и вердиктом,
   который вычисляет программа, а не модель.
4. **Экономика токенов как ограничение процесса:** always-context vs по
   требованию, H11–H15, маршрутизация моделей по блокам.
5. **План как документ для дешёвого исполнителя** с протоколом DECIDED/FORK.
6. **Безопасность и сбои — в AC на этапе спеки** (abuse cases, failure modes,
   baseline-5), документация до кода интеграции как жёсткие ворота.
7. **Самоизмерение агента:** здоровье ответов, решений, хуков; живые
   канарейки; мутационная проверка правил.
8. **Реестр дефектов по классам** с лестницей эскалации к машинной защите.
9. **Журнал отвергнутых вариантов**, чтобы не предлагать их снова.
10. **Портируемость между харнессами и провайдерами** моделей.

### 5.4 Пробелы STC относительно AI-DLC и классики

| Пробел | У кого есть | Насколько важно |
|---|---|---|
| **Эксплуатация продукта**: мониторинг, инциденты, пост-мортем, SLO | классика; AI-DLC — фаза Operations | высокая, если STC ведёт проекты с продом |
| **Reverse engineering как артефакт** для существующего кода | AI-DLC | средняя: инструменты есть (граф, снимок, zoom-out), документа нет |
| **НФТ и инфраструктура как отдельные этапы проектирования** | классика; AI-DLC (NFR Design, Infrastructure Design) | средняя: частично закрыто флагами профиля и блоком OBS |
| **Трассировка «требование → тест»** | классика (RTM) | средняя: AC — чеклист, без связи с тестами |
| **Одобрение после каждой стадии** | AI-DLC | низкая-средняя: STC сознательно ставит ворота только на выход из плана и на развилки |
| **Состояние процесса по фиче в одном файле** (+ журнал аудита) | AI-DLC | средняя: статус размазан по доске задач, спеке, транскриптам; у Roundtable свой протокол |
| **UAT / приёмка с пользователем** как этап | классика | низкая для личного харнесса |
| **Командная работа** (несколько людей, моб-ритуалы) | классика; AI-DLC | низкая сейчас: STC рассчитан на одного пользователя |
| **Мультивендорное ревью реализации** | — (своя задумка, Б14) | запланировано, вне MVP |

## 6. Попутные находки в репозитории

Не относятся к сравнению напрямую, но всплыли при чтении — это расхождения
между документами:

1. **Ссылки на нумерованные шаги PEV устарели.** `pev.md` сейчас содержит
   разделы Plan / Delegation / Execute / Verify и нумерованный список из 6
   пунктов плана, но другие файлы ссылаются на «Plan step 2/3/4», «pev Step 4»,
   «pev § Skills», «`pev.md` § Step 2»:
   `core/skills/council/SKILL.md:3,17,28`, `core/commands/to-spec.md:3,35`,
   `core/commands/to-tasks.md:42,49`, `core/memory/skills_triggers.md:18-20,106,155`,
   `core/memory/playbook.md:166`, `core/templates/new-project.md:152`.
2. **Два словаря исполнителей и моделей.** `pev.md` и `behavior.md` говорят
   уровнями Codex (Luna / Terra / Sol / Astra), а `/to-tasks` и playbook —
   `builder / cleanup / sub-sonnet / cheap-session / main` и `sub-haiku`;
   шаблон доски задач (`core/templates/vault/tasks-board.md`) —
   `exec:: agent · main`. Для одного поля `exec` три разных набора значений.
3. **«Council сводит результаты ×3»** (`code_standard.md` §7,
   `code-reviewer/SKILL.md`) — при этом навык Council описан как пять ролей
   для плана или исследования. Слово используется в двух смыслах.
4. **Делегирование в Roundtable** (`docs/roundtable.md` §14: «по умолчанию main
   исполняет всё сам; делегирование — по слову Антона») противоречит общему
   режиму оркестратора (FR-28, `pev.md`: делегировать каждый независимый
   ограниченный поток). Возможно, это осознанное исключение для этого
   проекта — тогда стоит так и написать.
